# FraudGuard

Микросервис скоринга банковских транзакций в реальном времени. Принимает поток платежей через REST API, прогоняет через движок правил, вычисляет индекс риска от 0 до 100 и отсекает подозрительные операции до проведения списания.

В проект входит рабочий веб-терминал для сотрудников финансового мониторинга с симулятором атак, фильтрами и выгрузкой отчётов.

---

## Ключевые архитектурные решения

Проект реализован как практическая демонстрация паттернов для банковского транзакционного скоринга:
- Защита от дублирования транзакций через двухфазную проверку ключей идемпотентности (`Idempotency-Key`).
- Расширяемый движок правил без монолитных `if-else` (паттерн Strategy).
- Применение гео-математики (формула гаверсинусов) для выявления физически невозможных перемещений (> 800 км/ч).
- Полное покрытие тестовыми сценариями (22 юнит- и интеграционных теста).

## Архитектура и логика скоринга

```
HTTP Запрос (с Idempotency-Key)
           │
           ▼
┌───────────────────────┐      Ключ уже обработан?
│ Fast-Check Idempotency├──────────────────────────────► [Возврат сохранённого результата]
└──────────┬────────────┘
           │ Нет
           ▼
┌───────────────────────┐
│     Rule Engine       │
│  - AmountThreshold    │
│  - VelocityBurst      │
│  - ImpossibleTravel   │
│  - DeviceAnomaly      │
└──────────┬────────────┘
           │
           ▼
┌───────────────────────┐
│  Расчёт Risk Score    │
│  (взвешенная сумма)   │
└──────────┬────────────┘
           │
           ├── Risk Score >= 70 или Critical Rule  ──► REJECTED (Блокировка)
           ├── Risk Score >= 35 или High Rule      ──► MANUAL_REVIEW (Ручной пересмотр)
           └── Иначе                               ──► APPROVED (Одобрено)
```

### Реализованные правила

| Правило | Логика детекции | Влияние на скор |
|---|---|---|
| `AmountThresholdRule` | Разовый перевод выше 150 000 ₽ или всплеск в 5+ раз выше среднего чека клиента | +35...+75 (Medium / Critical) |
| `VelocityRule` | Серия из 4+ операций по одной карте за 60 секунд | +40...+60 (Medium / High) |
| `ImpossibleTravelRule` | Скорость между последовательными операциями > 800 км/ч (по координатам городов) | +70 (High) |
| `SuspiciousDeviceRule` | Использование одного `device_id` тремя и более разными аккаунтами (признак фермы) | +30...+50 (Medium / High) |

## Быстрый запуск

### 1. Клонирование и установка окружения

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd fraudguard

python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/macOS:
source .venv/bin/activate

pip install -e ".[dev]"
```

### 2. Запуск сервиса

```bash
uvicorn app.main:app --reload --app-dir src --host 127.0.0.1 --port 8000
```

После старта доступны:
- Веб-терминал мониторинга: http://127.0.0.1:8000/
- Интерактивная документация Swagger: http://127.0.0.1:8000/docs

## Архитектурные компромиссы и масштабирование

В прототипе состояние хранится в потокобезопасном in-memory репозитории (`threading.Lock`). Это упрощает локальный запуск в один клик без поднятия внешних контейнеров.

Для промышленной эксплуатации под нагрузкой от 20 000 до 50 000 RPS архитектура эволюционирует следующим образом:

1. **Скользящие окна и кэш:** вынос счетчиков частоты операций в Redis Sorted Sets (`ZADD`, `ZREMRANGEBYSCORE`) со встроенным TTL, что снижает поиск до $O(\log N)$.
2. **Распределенная идемпотентность:** атомарная двухфазная блокировка на уровне Redis `SETNX` с фазой `PROCESSING` для исключения гонок при параллельных запросах.
3. **Асинхронная аналитика:** разбиение на синхронный шлюз проверки стоп-листов (SLA < 15 мс) и потоковую обработку в Apache Kafka с партиционированием по `account_id` для предотвращения race conditions.
4. **Хранение аудита:** сохранение журналов в распределённые базы данных (PostgreSQL для транзакций, ClickHouse для аналитики).
